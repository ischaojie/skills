# Python for Humans 编码原则

> "软件应该服务于人类，而不是让人类去适应机器。"
> — Kenneth Reitz

## 核心哲学

### 1. 以人为本 (Human-Centered)

软件应该服务于人类，而不是让人类去适应机器。API 设计应该优先考虑人类的心智模型，而非计算机科学的抽象概念。

**实践要点：**
- 设计 API 时从用户视角出发，而非技术实现视角
- 让工具符合人类的思维方式，而非强迫开发者像计算机一样思考
- 减少认知负担，让强大的工具对普通开发者触手可及

### 2. 简洁优于复杂 (Simple is Better than Complex)

每一层不必要的抽象都会给开发者带来摩擦。优秀的 API 应该让常见任务变得简单直接。

**实践要点：**
- 90% 用例原则：为最常见的场景优化，使其变得极其简单
- 为边缘情况提供逃生舱口，但不要让它们干扰主要接口
- 复杂性容易添加，但几乎不可能移除

### 3. 美观优于丑陋 (Beautiful is Better than Ugly)

接口应该感觉自然且令人愉悦。好的 API 不仅功能正确，使用起来也应该是一种享受。

**实践要点：**
- 追求直观、优雅的接口设计
- 参数命名应该符合人类对概念的自然理解
- 一致的命名和行为模式

### 4. 一种明显的方式 (One Obvious Way)

对于常见任务，应该只有一种明显的方式去完成。减少决策瘫痪和认知负担。

**实践要点：**
- 避免提供多种方式完成同一件事的诱惑
- 让正确的做法成为最简单的做法
- 遵循惯例和约定优于配置

## API 设计原则

### 5. 优化 90% 用例 (Optimize for the 90% Use Case)

不要试图在主要接口中处理每一个边缘情况。专注于让最常见的场景变得简单。

**示例对比：**

```python
# 反例：urllib2 - 过于复杂的接口
import urllib2
req = urllib2.Request('http://example.com')
req.add_header('User-Agent', 'Mozilla/5.0')
response = urllib2.urlopen(req)
data = response.read()

# 正例：Requests - 简洁直观
import requests
response = requests.get('http://example.com')
data = response.text
```

### 6. 一致性 (Consistency)

HTTP 方法（GET、POST、PUT、DELETE 等）应该按照开发者期望的方式工作，参数应该自然地映射到人类对网络请求的心智模型。

**实践要点：**
- 方法命名和行为保持一致
- 参数顺序和命名遵循可预测的模式
- 错误处理方式统一

### 7. 优秀的文档 (Great Documentation)

文档应该以人为本，将读者视为寻求实用解决方案的聪明人，而非需要详尽规范的机器。

**实践要点：**
- README 是第一印象，决定库是否被采用
- 提供清晰的安装说明
- 分享经过实战检验的最佳实践
- 提供有主见的指导，帮助开发者快速做出好决策

### 8. 持续简化 (Continuous Simplification)

随着库的发展和新功能的增加，保持 API 简洁变得越来越有挑战性，但仍然是必不可少的。

**实践要点：**
- 在添加新功能时保持克制
- 定期审视 API 是否可以进一步简化
- 勇于废弃和移除不必要的复杂性

## 设计检查清单

在设计和评估 API 时，问自己：

- [ ] **用户视角**：这个 API 是否符合用户的思维方式？
- [ ] **常见用例**：90% 的用户能否用最少的代码完成任务？
- [ ] **直观性**：接口是否自然、不言自明？
- [ ] **一致性**：命名和行为是否与用户的期望一致？
- [ ] **文档**：README 是否清晰、实用、有指导性？
- [ ] **简单性**：是否避免了不必要的抽象和配置？
- [ ] **美观性**：使用这个 API 是否令人愉悦？

## 总结

"Python for Humans" 不仅是一套技术原则，更是一种关于技术角色的伦理立场——技术应该成为扩展人类能力的手段，而非限制。这些原则适用于所有编程语言和框架，核心始终不变：**致力于人类福祉**。
